Git desde cero: los comandos esenciales del control de versiones

Git es el sistema de control de versiones más usado del mundo: casi todos los proyectos de software, grandes o pequeños, viven en un repositorio de Git. Si estás aprendiendo a programar o quieres trabajar en equipo, entender Git no es opcional. Esta guía te lleva de cero a dominar el flujo de trabajo diario: inicializar un repo, hacer commits, crear ramas, trabajar con remotos y deshacer errores.

¿Qué es Git y por qué usarlo?

Un sistema de control de versiones registra cada cambio que haces en tus archivos a lo largo del tiempo. Piensa en él como una máquina del tiempo para tu código: puedes ver quién cambió qué, cuándo y por qué, y volver a cualquier estado anterior si algo se rompe.

Git es distribuido: cada persona tiene una copia completa del historial en su máquina, no solo un servidor central. Esto significa que puedes trabajar sin conexión, que cada copia es un respaldo y que los equipos pueden colaborar en paralelo sin pisarse.

Instalación y configuración inicial

Instala Git en tu sistema:

  • Windows: descarga el instalador desde git-scm.com. Incluye una terminal llamada Git Bash.
  • macOS: brew install git o simplemente instala Xcode Command Line Tools.
  • Linux (Ubuntu/Debian):
sudo apt update
sudo apt install git -y
git --version

Después de instalar, configura tu identidad. Git la usa para marcar cada cambio con tu nombre y correo:

git config --global user.name "Tu Nombre"
git config --global user.email "tu@correo.com"

Verifica tu configuración con git config --list.

Empezar un proyecto: git init

Entra en la carpeta de tu proyecto y ejecuta:

cd mi-proyecto
git init

Esto crea una carpeta oculta .git que almacena todo el historial. Ahora tu carpeta es un repositorio de Git. Advertencia: nunca inicialices Git dentro de otro repositorio, y usa el archivo .gitignore para evitar subir archivos pesados o sensibles como node_modules, claves o archivos de build.

El ciclo básico: add y commit

El flujo de trabajo más básico tiene tres pasos: modificar archivos, agregarlos al área de preparación (staging) y guardar un commit.

# Ver el estado del repositorio
git status

# Agregar un archivo concreto al staging
git add index.html

# Agregar todos los archivos modificados
git add .

# Guardar un commit con un mensaje descriptivo
git commit -m "Agrega la página de inicio"

git add lleva los cambios al área de staging, que es como una "caja" donde preparas lo que vas a incluir en el siguiente commit. git commit guarda una captura permanente de esa caja en el historial, con un identificador único (hash), autor, fecha y mensaje.

Ver el historial: git log

git log
git log --oneline
git log --oneline --graph --all

git log --oneline te muestra cada commit en una línea con su hash abreviado y su mensaje. Es el resumen diario que todo desarrollo utiliza.

Ramas: git branch

Una rama es una línea de desarrollo independiente. Te permite experimentar o trabajar en una funcionalidad sin afectar el código principal. La rama principal por defecto es main (antes master).

# Listar ramas
git branch

# Crear y moverte a una rama nueva en un solo paso
git switch -c feature/nuevo-diseño

# Cambiar de rama
git switch feature/nuevo-diseño

Cuando termines el trabajo de tu rama, la íntegras (merge) en la principal:

git switch main
git merge feature/nuevo-diseño

Git intenta unir los cambios automáticamente. Si dos personas cambiaron la misma línea de código aparece un conflicto de fusión: Git marca las zonas conflictivas en los archivos para que decidas manualmente qué versión conservar.

Trabajar con un repositorio remoto

El repositorio remoto (por ejemplo en GitHub, GitLab o Bitbucket) es la copia compartida en un servidor. Para conectar tu local con un remoto:

# Clonar un repositorio existente
git clone https://github.com/usuario/repo.git

# Conectar un proyecto local a un remoto
git remote add origin https://github.com/usuario/repo.git

# Subir tus commits a la rama main del remoto
git push origin main

# Descargar los cambios del remoto
git pull origin main

El flujo completo en equipo se resume en: git add → git status → git commit → git push para publicar, y git pull para recibir el trabajo de los demás antes de empezar. Practica siempre git pull antes de codear para evitar conflictos innecesarios.

Deshacer cambios

No pasa nada si te equivocas. Git está diseñado para rescatar te:

# Ver qué cambiaron respecto al último commit
git diff

# Descartar cambios de un archivo sin preparar
git restore index.html

# Quitar un archivo del staging (sin perder cambios)
git restore --staged index.html

# Deshacer el último commit preservando los cambios en el staging
git reset --soft HEAD~1

# Mover el proyecto a un commit anterior (¡cuidado! afecta al historial)
git reset --hard <hash>

Consejo: recurren a git reset --hard solo cuando estés seguro, porque descarta los cambios de forma permanente localmente.

Buenas prácticas

  • Mensajes de commit claros: comienzan con un verbo en infinitivo o imperativo: "Corrige el bug de autenticación".
  • Commits pequeños y atómicos: una funcional refactoria por commit. Es más fácil hacer seguimiento y revertir.
  • .gitignore siempre: evita subir node_modules, .env, dist y archivos de clave.
  • Nunca comits de secretos: una vez publicado en Git, es casi imposible borrarlo de verdad.
  • Pull antes de push: actualizar tu local evita la mayoría de los conflictos.

Conclusión

Git es una habilidad diaria, no un lujo. Con init, add, commit, branch, merge, remote y restore ya tienes el 90% de lo que cualquier desarrollador usa. Ahora abre tu terminal, crea un proyecto y repite el ciclo varias veces. La práctica con timer es la única forma de hacerlo natural.

Si te tropiezas con errores como push rejected o conflictos, consulta la guía Errores comunes de Git y cómo solucionarlos.
